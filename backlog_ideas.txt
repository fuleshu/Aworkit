Your question #3 — can compaction run on the running LLM line instead of a parallel one?
Short answer: it isn't actually parallel — it's sequential, and it's already using the same model. The slowness you're feeling is a different (real) cost.

What the code actually does (SummaryProvider in compaction/provider.rs, and the selectedBinding: None in your log):

Compaction fires inside manage_model_context, before the next main turn — it does not run a concurrent second thread.
You have no separate summarization model configured (summary_target is None), so the summary uses the same local model, not a second one.
What's expensive is that the summary request re-sends the shadowed history (~125K+ tokens) as input, and the local runner must prefill all of it again — a fresh forward pass over the whole prefix. That's the slow + memory-heavy part (the KV cache for that huge input), not a second model.
So "run it inline on the already-running line" doesn't map onto stateless LLM APIs: each request independently pre-fills its input, and the summary has to re-read the history it's summarizing. There's no way for the summary to reuse the in-flight generation's compute.

Options that would actually help (none are quick one-liners):

Prefix / KV-cache reuse — if your local runner (llama.cpp / vLLM / etc.) supports prompt prefix caching, the summary's input (a prefix of the main context) could reuse the cached KV instead of re-prefilling. Aworkit doesn't currently do this; it would need runner awareness + wiring. This is the real "inline" answer.
Compaction fires less often now — your fix #2 already moves the trigger from ~50% to ~80%, so you'll hit this expensive path far less frequently.
Keep summary_target unset (it already is) so you never load a second model.

optional budget gate for a Chat (idea, 2026-09-23):
Today nothing cumulative caps a run, by design: the worker LimitLedger exists (crates/aworkit-workflow-worker/src/limits.rs) but the desktop freezes tokens, cost and deadline to sentinels (NO_AGGREGATE_RUN_DEADLINE_EPOCH_MILLIS), agent-internal provider calls are not turn-capped (legacy_maximum_turns: None), and a graph loop's iteration bound is optional — no bound means it repeats until its frozen exit condition holds, and only Stop ends it.
The idea is an opt-in gate the user chooses deliberately, not a platform cap:
- an input in the chat surface, e.g. a budget field beside the composer, set before the first input is committed and then frozen into the Chat with the rest of the execution context;
- the frozen value stays visible (composer, Run details, and the loop/agent evidence that charges it);
- exhaustion takes an explicit declared outcome — the same fallback/limit route loops already use, or a turn that stops with a stated reason — and must never surface as a provider failure;
- an absent field means exactly today's behaviour, so nothing changes unless the user asks for a gate;
- it has to cover agent-internal model-tool loops, not only graph loops, since those are uncapped today.
Open questions: granularity (per Chat, per turn, per node), what counts against it (provider calls, tokens, cost, wall clock), whether the composer is the right home or a Run-details control is, and how a resumed or steered Chat continues a partly consumed budget.
