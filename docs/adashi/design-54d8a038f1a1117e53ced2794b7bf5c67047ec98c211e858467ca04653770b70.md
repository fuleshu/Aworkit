# Failure policy: no limit ends a run; every condition is reported

Normative model for what may terminate an Agent node, decided 2026-09-27 after the recorded run `chat.e1608e3b0f642edccf7dcb59588deb2a61dbd0fb` died 61 minutes into its work; amended 2026-10-07 to let a provider that repeatedly refuses the same request end the pass, and to carry the provider's own refusal text.

## The incident this replaces

That Chat spawned one subagent. The child started background processes whose records landed under the delegating invocation's scope, so the child's own scoped notice and controls could not see them; 49 of them stayed `finished; output not collected`. On the parent's next turn the completion notice enumerated all 49 - one 100-byte line per job around a 391-byte frame, 5291 bytes - and the dispatch precondition on `retryNotice` (4 KiB) rejected the request. The rejection was classified as a context-preparation failure, so the Agent node failed with `context preparation failed: Invalid model context: provider failed: provider tool request is invalid` and the run stopped with `outcome_uncertain`. The model, the tools and the task were all healthy.

## Invariants

1. Exactly four classes of condition terminate an Agent node: the model's final answer; user cancellation; an unrecoverable refusal; and a provider that refuses the same request repeatedly with no accepted turn in between. An unrecoverable refusal is only the trusted core refusing to durably record an exchange. An accepted turn that returns neither an answer nor a tool call is *reported and continued*, not a termination: the recorded benchmark turn that spent 65,536 output tokens on reasoning and returned no text is exactly the case the loop has to survive. The repeated-refusal ending is a fact about the dispatch, not a budget on the Agent's work: when the provider refuses the request nothing reaches the model, so no Agent decision is pending and no new report is possible. It stops the pass carrying the provider's own bounded refusal text.
2. Every other condition - provider, transport, contract, context preparation, tool invocation, tool settlement, budget, counter, deadline or limit - is reported to the model as a bounded notice and the loop continues, except the repeated identical refusal in 1.
3. A bound sizes the notice, never the run. Truncation is explicit: the notice states what it omitted and how to retrieve it (for jobs, `job_list`).
4. Counters, budgets and token totals are telemetry. None is a termination control; there is no total model-turn, tool-call, recovery or notice cap. A repeated condition keeps being reported as a repeat reminder. The one ending that counts attempts is the identical provider refusal in 1, and what it counts is a dispatch fact - the same request refused again and again - never the Agent's progress.
5. Structural validation has two roles and two outcomes. An editor may reject a document and explain why; dispatch must degrade - bound, truncate or drop the advisory field - because a rejected dispatch is a dead run.
6. Reporting is durable. A reported condition is committed as an event, so a restart resumes on the same notice the model last saw instead of replaying the original failure.

## Consequences, accepted deliberately

A provider that never recovers is reported at a bounded rate; after ten *identical* refusals with no accepted turn in between - a threshold high enough to ride out a reset connection or a dropped stream, and cleared by any accepted turn - the pass ends carrying the provider's own bounded refusal text, so a misconfigured provider, a provider-side outage or a harness bug is actionable instead of an endless loop. A failure that varies keeps being reported, and the user's stop remains the exit for everything else. The same reasoning covers the diagnostic itself: a refusal that names the offending field is worth more than the status it arrived with. A job inventory of any size is summarized, not enumerated. A context that cannot be projected under the current tool selection is declined and the pass continues on its own context.

## Amendment 2026-11-25: a delegated child reports back, and a provider answer is classified

Recorded after run `chat.c4dbf38e958dce7a2926a61926b9b86628776d72`: six delegated children on a 1 M-context model spent EUR 20 and produced no merged result. The parent Agent node was ended by the repeated-refusal rule at 18:47:42 carrying the provider's 429 text (`You exceeded your spend-based rate limit`), while one child accumulated 107 refusals and was only marked failed at 18:49:10. The run then held 12 open spans with no event for 2 h 25 min until the user cancelled it, and 297 failed attempts carried no cause and no usage.

### A. Delegated work is a tool call, so its outcome is a tool result

1. Every terminal child status - `completed`, `failed`, `cancelled` - is delivered to the delegating agent as one bounded tool result on its next turn, and committed as an event before dispatch so a restart re-delivers it instead of replaying the dispatch.
2. A child's failure never re-runs the child and never ends the delegating node: it is a condition reported under invariant 2, and the delegating model decides what happens next.
3. Silence is not progress. A child that stops producing events without a terminal status is a stall and is reported as one - child id, last committed sequence and the age of that sequence - so no child holds a run open while its delegator hears nothing.
4. The notice summarizes rather than transcribes: counts, the child's final text or bounded refusal excerpt, and how to retrieve the rest (invariant 3).
5. A parent's failure cascades. When an Agent node terminates for any reason, its live children are cancelled and their terminal statuses committed in the same pass, so no span outlives the pass that owns it.

### B. A provider answer is classified, and the class decides the reaction

A provider failure is not one condition. Before anything is re-dispatched, the failure is classified and the harness changes state accordingly:

| class | recognised by | required reaction |
| --- | --- | --- |
| spend or quota limit | a 429 or 402 whose text names a spend, quota, credit or billing limit | stop immediately and end the pass with the provider's bounded text; the limit belongs to the account, so every other pass and child dispatching to that provider in the same Chat stops as well; no retry can succeed until a human changes the limit |
| rate limit | 429 without a spend or quota meaning | wait for the provider's `Retry-After` when present, otherwise bounded exponential backoff with jitter; re-dispatch only after the wait; end the pass with the provider's text when the wait budget is spent |
| transient | 5xx, reset stream, timeout | bounded backoff retry, then end the pass with the provider's text |
| authentication or configuration | 401, 403, unknown model id, unusable endpoint | no retry; fail the pass naming the provider and the setting to fix |
| context too large | context-length rejection | compact or trim once, then re-dispatch; never an identical resend |

1. "React" means the harness waits, backs off, compacts or stops. Re-sending the same request without consuming the provider's answer is a defect, not resilience.
2. The class, the provider's bounded text and the chosen reaction are recorded on the attempt, so Run details shows both why the call failed and what was done about it. A failure body that names neither is unacceptable; `Canonical model result settled.` on 297 failed attempts is the anti-pattern.
3. The repeated-refusal rule counts a class, not a byte-identical request. A loop whose payload changes with every retry - a notice, a turn counter - can never reach the threshold: the guard ended the parent after ten refusals and let a child run to 107. Classification must be stable across retries by construction, and a spend or quota limit ends the pass on its first occurrence.
4. Backoff and wait budgets bound dispatches, never the agent's work, so invariant 4 stands: no counter ends a run, and any accepted turn clears the refusal count.
5. A spend or quota limit is a fact about the account, not about one model call: the first observation stops every pass and delegated child dispatching to that provider in the same Chat. Six children must not each discover the same limit.
6. Regression tests pin both halves: a failed child produces a parent notice, a cancelled parent leaves no live child, a child that stalls produces a stall notice, one child observing a spend limit stops its siblings, and each class above maps to its reaction rather than to a resend.

## Non-responsibilities

This policy does not decide what a notice says, how compaction reduces a context, or which provider response counts as empty. Bounded notice content belongs to the producer; the termination set belongs here.
