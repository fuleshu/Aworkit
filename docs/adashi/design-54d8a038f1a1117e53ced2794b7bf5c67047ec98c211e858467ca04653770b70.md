# Failure policy: no limit ends a run; every condition is reported

Normative model for what may terminate an Agent node, decided 2026-09-27 after the recorded run `chat.e1608e3b0f642edccf7dcb59588deb2a61dbd0fb` died 61 minutes into its work; amended 2026-10-07 to let a provider that repeatedly refuses the same request end the pass, and to carry the provider's own refusal text.

## The incident this replaces

That Chat spawned one subagent. The child started background processes whose records landed under the delegating invocation's scope, so the child's own scoped notice and controls could not see them; 49 of them stayed `finished; output not collected`. On the parent's next turn the completion notice enumerated all 49 - one 100-byte line per job around a 391-byte frame, 5291 bytes - and the dispatch precondition on `retryNotice` (4 KiB) rejected the request. The rejection was classified as a context-preparation failure, so the Agent node failed with `context preparation failed: Invalid model context: provider failed: provider tool request is invalid` and the run stopped with `outcome_uncertain`. The model, the tools and the task were all healthy.

## Invariants

1. Exactly four classes of condition terminate an Agent node: the model's final answer; user cancellation; an unrecoverable refusal; and a provider that refuses the same request repeatedly with no accepted turn in between. An unrecoverable refusal is only the trusted core refusing to durably record an exchange. An accepted turn that returns neither an answer nor a tool call is *reported and continued*, not a termination: the recorded benchmark turn that spent 65,536 output tokens on reasoning and returned no text is exactly the case the loop has to survive. The repeated-refusal ending is a fact about the dispatch, not a budget on the Agent's work: when the provider refuses the request nothing reaches the model, so no Agent decision is pending and no new report is possible. It stops the pass carrying the provider's own bounded refusal text.
2. Every other condition - provider, transport, contract, context preparation, tool invocation, tool settlement, budget, counter, deadline or limit - is reported to the model as a bounded notice and the loop continues, except the repeated identical refusal in 1.
3. A bound sizes the notice, never the run. Truncation is explicit: the notice states what it omitted and how to retrieve it (for jobs, `job_list`).
4. Counters, budgets and token totals are telemetry. None is a termination control; there is no total model-turn, tool-call, recovery or notice cap. A repeated condition keeps being reported as a repeat reminder. The one ending that counts attempts is the identical provider refusal in 1, and what it counts is a dispatch fact - the same request refused again and again - never the Agent's progress.
5. Structural validation has two roles and two outcomes. An editor may reject a document and explain why; dispatch must degrade - bound, truncate or drop the advisory field - because a rejected dispatch is a dead run.
6. Reporting is durable. A reported condition is committed as an event, so a restart resumes on the same notice the model last saw instead of replaying the original failure.

## Consequences, accepted deliberately

A provider that never recovers is reported at a bounded rate; after ten *identical* refusals with no accepted turn in between - a threshold high enough to ride out a reset connection or a dropped stream, and cleared by any accepted turn - the pass ends carrying the provider's own bounded refusal text, so a misconfigured provider, a provider-side outage or a harness bug is actionable instead of an endless loop. A failure that varies keeps being reported, and the user's stop remains the exit for everything else. The same reasoning covers the diagnostic itself: a refusal that names the offending field is worth more than the status it arrived with. A job inventory of any size is summarized, not enumerated. A context that cannot be projected under the current tool selection is declined and the pass continues on its own context.

## Evidence

## Non-responsibilities

This policy does not decide what a notice says, how compaction reduces a context, or which provider response counts as empty. Bounded notice content belongs to the producer; the termination set belongs here.
