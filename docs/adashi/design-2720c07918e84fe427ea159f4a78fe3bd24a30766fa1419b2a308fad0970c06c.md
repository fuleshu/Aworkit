# Validate/freeze hardening: implementation record (task 184)

Status: implementation record, 2026-10-04. Supersedes nothing; it records what actually landed against the proposal `aworkit.validate_freeze_hardening` and what remains. Commits are on `main`.

## What changed

### P0 - remove the outage class (commit 53691c5)

- Every nested snapshot hash is now verified over the stored JSON sub-value (Rule A), not over today's decoded struct: workflow, model tier, provider, model, each tool `toolHash`, and the project/workspace hashes. A record a different build wrote with an additive default field still verifies; a tampered stored value is still rejected byte-exactly.
- Durable records no longer carry `deny_unknown_fields`, so a record with an unknown key (the `bridgeServerId` outage) decodes; unknown keys are dropped. The Settings load path keeps an explicit unknown-key check so a human's typo is still reported.
- Frozen-record reads filter by the raw stored `chatId` before decoding, and the app-open/repair scan skips an unreadable record instead of failing open. One bad old record can no longer break listing Chats, starting a new Chat, or application open.
- Compatibility tests over hand-written stored JSON cover the unknown-nested-key tolerance, the missing-field case, the tamper case and the unrelated-bad-record case, plus an Adashi QA job.

### P1 - validation cannot kill a message (commit 2dc867f)

- Run-path shape and availability refusals degrade to committed notices and dropped bindings; hard failure is reserved for the three conditions the failure policy permits.
- A saved workflow edited mid-Chat into a non-executable state falls back to the frozen snapshot with a notice.
- Send readiness gates on the selected/frozen workflow's core verdict, not the library default.
- The reachable `.expect("at least one model tier is resolved")` start-path panic is gone; it is a typed refusal naming the fix.
- The validate-what-was-just-written checks are gone (the write path hashes the value it builds; the read path verifies stored bytes).
- Saving still preserves unknown node types and now surfaces the core's save-time verdict `{ executable, rule, remedy }` to the editor.

### P2.3 - one digest rule (commit ddbcf08)

`runtime/digest.rs` is the single RFC 8785 (JCS) + SHA-256 implementation; the duplicate `canonical_hash`/`digest`/`is_sha256` copies across history, pipeline, tool_loop, approvals, project scope and MCP helpers delegate to it. Output bytes are unchanged. `approvals::digest` is now explicitly key-order independent, with the previous bytes pinned by `approval_grant_digests_keep_their_bytes`.

### P2.4 - versioned frozen records (commit ddbcf08)

`schemaVersion` now selects validation. The current version validates as before. An older version routes through an explicit (currently empty) migration table and is refused by name. An unknown newer version is byte-verified (outer `context_hash` over the stored bytes plus the size bound) and returned read-only with a notice instead of failing the read; the Chat opens read-only with that notice and refuses execution. Tamper detection is byte-exact in all three branches.

## Deviations and remaining work

- **P2.1 one capability registry: not implemented.** Nothing was deleted; the prefix tests and fixed id sets remain.
- **P2.2 one schema verdict: not implemented.** The editor still carries the TypeScript twin validator (`workflowExecution.ts`) and the known Rust/TS drift pairs.
- **P2.5 (redundant re-validation, compiled-pass caching): not implemented.** The safe half is scoped: skip the duplicate catalog validation for a document validated earlier in the same process, keeping the full check for a record replayed from the store; the compiled-pass cache by snapshot hash was judged risky without tamper-masking tests.
- **P2.6 (path/rule/value diagnostics): not implemented.** The large conjunct validation chains are untouched; only the version-gate messages name the version.
- **Blocked inside P2.3:** `command_fingerprint` (service.rs) still digests in field-declaration order. `UiCommandInput`'s field order is not JCS-sorted, so switching it to the shared rule would change stored `start_command_hash` bytes inside already-frozen contexts and staged commands. This needs a stored-record migration, not a digest change.
- **Reported non-change in P1:** a frozen graph this build can no longer compile still refuses the pass, because an uncompilable graph has no degraded form. Every other shape/availability condition on the run path degrades.
- **Known limitation of the P2.4 gate:** the newer-version read-only path is only as tolerant as serde's required fields; a future build that renames or removes a currently required field would fail in serde before the gate runs. Full tolerance needs field-level optionality or a raw-`Value` read path and belongs with P2.1/P2.5.
