# MCP session recovery: reconnect instead of requiring an application restart

A transport loss marks an MCP session degraded. A degraded session refuses every later call before dispatch, so without recovery one slow or flaky call disables that server for the rest of the application run.

## Policy

- **Recover before the next call.** When a Run's MCP call returns `SessionDegraded`, the runtime reconnects once with `McpSessionManager::reconnect` and then dispatches that call. The call had not started, so this is not a replay.
- **Never replay a dispatched call.** A timed-out or interrupted call keeps its uncertain or definitely-not-started outcome; only the transport is recovered. The call that lost its transport is never replayed.
- **A Run call may take minutes.** A production Run call gets a multi-minute request ceiling because a tool such as `adashi_qa run_jobs` blocks until its QA script finishes. The one-shot discovery probe keeps its short bound. A call that still outlives the ceiling is reported as uncertain and the session recovers on the next call, so a long job can be polled instead of bricking the server.
- **An explicit reconnect reaches live sessions.** A Settings reconnect reconnects the degraded sessions for one server across every live Run without restarting the application.

## Not decided here

This does not decide which condition degrades a session, how a QA tool should schedule long work, or whether a dispatched effect happened; those remain the session manager's dispatch milestones and the tool's own contract.
