# ComfyUI integration

Aworkit ships a first-class ComfyUI integration with its own Settings tab. It turns a running ComfyUI server and its API-format workflows into native agent tools, helps author the tool parameters with a model, and owns ComfyUI's connection lifecycle. A workflow tool is executed in process by the Rust host: no bridge subprocess, no MCP server and no host interpreter are involved.

## Scope

The integration adds five user-visible capabilities:

1. **A dedicated ComfyUI Settings tab.** One section holds the ComfyUI server endpoint, the optional local installation folder and launch arguments, the workflow tools, and the workflow-authoring assistant. It is a normal Settings section, so dirty tracking, validation, save and reload are the existing Settings v2 paths.
2. **One native agent tool per ComfyUI API workflow.** Each enabled workflow tool is a capability with the stable id `comfyui.<tool id>` whose model-facing name, description and JSON schema are generated from the typed parameter list the Settings tab edits. The model calls it like any bundled tool; a successful call returns the produced images as immutable image evidence and as vision input.
3. **Two read-only authoring helpers.** `comfyui.list_node_types` searches the live `/object_info` catalog under a bounded page, and `comfyui.get_workflow` returns the API graph of one configured workflow tool. Both are approval-free native capabilities.
4. **Model-assisted parameter authoring.** An "Auto create parameters" action reads an API workflow JSON, asks the model configured for `tier:balanced` to choose reasonable parameters and bind each one to a real workflow input, and proposes the result for review. A binding is accepted only when the referenced node input exists in that exact workflow.
5. **Connection and optional local start.** Aworkit probes `GET /system_stats`, reports reachability and the server's ComfyUI version, and, when the user configured a local installation folder and enabled local start, launches the ComfyUI server and waits for readiness before queueing work.

## Why the tools are native

A workflow tool's schema is data derived from Settings, so it is the same kind of dynamic tool class as an MCP function: it is frozen with the Run, brokered, approved and settled by evidence exactly like any other capability. Only its wire protocol differs, and it needs none. Running the workflow is local HTTP to the configured ComfyUI server, so the tool is executed in process by the desktop host instead of through a supervised sidecar.

That decision removes a duplicated implementation. The bounded ComfyUI HTTP client and API-workflow inspection already live in the Rust capability host; a script layer reimplemented them, required a host Python interpreter, needed a plugin package under the runtime data root, and surfaced the workflow tools only as one server-level MCP checkbox rather than named tools. The native tool surface is the single implementation.

## Workflow tool model

A workflow tool is a stable id, a display name, a description, a reference to one ComfyUI API-format workflow JSON, an enabled flag, and an ordered parameter list. A parameter declares:

- its name, description, JSON type (`string`, `integer`, `number`, `boolean`) and whether it is required;
- an optional default and, for a bounded choice, its allowed values;
- the exact workflow binding: the node id and the input name the value is written to.

The binding is the security boundary. A parameter can only write to a node input that exists in the referenced API workflow. A workflow tool cannot invent a node, an input, a model filename or a downstream capability. Parameters that are not bound to a workflow input are rejected, and the generic override path is never exposed as a tool parameter. The two authoring helper ids are reserved, so a workflow tool can never shadow one.

## Freeze, admission and execution

The Settings section is the single enable decision, and it is resolved once, at the first input of a Chat:

- Every enabled workflow tool becomes a frozen binding whose configuration carries the endpoint, the workflow file and each `(node id, input name)` pair, together with the generated model-facing definition. A later Settings edit cannot change what a running Chat executes.
- The two authoring helpers freeze the endpoint and, for the workflow reader, the workflow table resolved from Settings.
- A workflow tool's descriptor is generated for the Run from the same Settings, recorded in the authority manifest by version and hash, and re-derived and re-checked at dispatch before the workflow runs. Because it is Settings-derived it is never registered in the frozen capability-host registry; the two helpers have compile-time schemas and are registered like any built-in capability.
- A call is refused before ComfyUI sees it when it carries an undeclared key, omits a required value, passes a null, uses the wrong JSON type, or selects a value outside the workflow's reported choice set.
- Execution reads the workflow JSON under a 2 MiB bound, writes only the arguments the model actually supplied into the frozen bindings, queues the prompt, waits for the history entry, and stores the produced file as immutable image evidence. The queue wait bounds one call, not the Run; a Run cancellation aborts the wait.

## Parameter authoring

Authoring is a bounded, tool-free model call from Settings, using the model the user mapped to `tier:balanced`:

- The host sends the API workflow JSON plus the list of its editable inputs. It never asks the model to run the workflow.
- The model answers with the tool identity, description and parameter list, each bound to a supplied node input.
- The host validates the answer against the workflow: every proposed binding must match a real editable input, types must be coherent with the current value, and names and descriptions are bounded. One format correction attempt is allowed, then the action fails closed.
- Nothing is saved automatically. The proposal lands in the Settings draft for the user to review, edit and save.

`tier:balanced` must resolve to an exact configured provider/model, the same requirement every workflow model node already has. When the tier is unconfigured or not exact, the action reports that instead of substituting a different model.

## Connection and local start

- Reachability is a bounded `GET /system_stats`. It reports reachability, the ComfyUI version when the server returns one, and the endpoint in every failure message.
- Local start is opt-in and only offered when a local installation folder is configured. Aworkit launches the configured program and arguments in that folder, then polls `/system_stats` until the server is ready or the startup deadline passes. A start that does not become ready is reported as a named failure with the captured startup output, not silently retried forever.
- Starting is an explicit user action or an opt-in setting; a Chat never spawns ComfyUI on its own initiative.

## Workflow authoring assistant

Besides the two built-in helpers, the ComfyUI tab can register an optional workflow-authoring MCP server that gives the agent ComfyUI node and workflow knowledge. That server is an ordinary configured MCP entry with the existing trust, transport, approval and evidence semantics; it is knowledge plus reads, never a second execution path, and it never bypasses the normal file and MCP tool authority.

## Failure and degraded behavior

- ComfyUI unreachable is a named failure that includes the endpoint and the fix; a tool call fails visibly and the Run continues.
- A workflow that produces no image output reports that explicitly.
- An unreadable, malformed or oversized workflow JSON is reported against that workflow tool and does not disable the others.
- The authoring helpers report an unreachable server, a catalog read the server refuses, and a workflow id that is not one of the frozen tools as named failures.
- Editing ComfyUI configuration never rewrites committed Run evidence, and a running Chat keeps the frozen tool definitions it started with.

## Evidence

The section version, the workflow-tool table hash, each frozen tool definition, the per-Run descriptor identity of a workflow tool, and each invocation's realized arguments are recorded per Run through the existing capability, approval and evidence paths. A produced image is stored as immutable image evidence. An authored parameter list records which model binding produced it and its token usage in the Settings action result; it is not a Run.

## Verification

A stub ComfyUI server covers the whole native path: one enabled workflow tool is frozen from Settings, admitted through its generated descriptor, dispatched in process, and its produced image is stored as evidence; an undeclared argument is refused before the server is contacted. The read-only helpers are covered by the bounded catalog page and the bounded workflow reader.
