# Tool plugins

A tool plugin is one installable folder that adds capabilities to Aworkit. It bundles one MCP server (the capability plus its configuration) and may bundle skill folders. Aworkit autosources a single plugin folder, lists what it finds, and runs nothing until the user installs and enables a plugin.

This document is the implementation reference for the plugin manager, the manifest, the transports, optional skills, settings and secret slots, side-effect hints, trust, the folder lifecycle, enablement, removal and update semantics, degraded behavior and platform behavior. It complements the narrower `docs/design-tool-plugins.md`.

## The three layers, and where the boundary is

- **Skill** - procedural knowledge: a folder with a `SKILL.md` file, optional scripts and resources. Portable, model-invocable and user-invocable. A skill carries no typed input or output and no side effects of its own.
- **MCP tool** - the capability with configuration: an executable command plus arguments, or an HTTP endpoint; credentials; a typed input schema and a typed result; side-effect annotations; approval. A tool is how the model acts.
- **Plugin** - the installable, versioned, trusted package that bundles MCP server(s) and optionally skill folders. The plugin is the trust and install unit; MCP is the only tool wire protocol.

Pure procedure is a skill, not a tool. A plugin that ships only a skill folder adds knowledge, not authority. The plugin concept is deliberately not called an "extension": one plugin concept covers both a local executable MCP server and a remote HTTP MCP server.

## Package layout

```
<plugin-folder>/
  tool-plugin.json          required: identity, transport, optional seed tool catalog
  <server executable or script>
  workflows.json            optional: plugin-owned configuration the server reads
  skills/<name>/SKILL.md    optional: skill folders the plugin contributes
  README.md                 optional
```

The whole folder is copied, so the server may read any relative file. Paths inside the package are resolved against the package folder at discovery time; an absolute path selects an installed interpreter or program, and a bare command name (for example `python` or `node`) is resolved from `PATH`. A relative path may never traverse out of the package folder.

## The plugin declaration

`tool-plugin.json` is version-1, owner-produced JSON. The concrete file name is scoped to this feature and is not a general extension standard.

```json
{
  "schemaVersion": 1,
  "id": "plugin.example",
  "name": "Example tools",
  "version": "1.0.0",
  "execution": { "transport": "stdio", "command": "python", "args": ["server.py"], "env": [] },
  "tools": [
    { "name": "echo", "description": "Return the message.", "inputSchema": { "type": "object" },
      "enabled": true, "annotations": { "readOnlyHint": true, "destructiveHint": false },
      "options": { "instructions": "Use echo to repeat text." } }
  ]
}
```

- Identity is a stable id, a display name and a version. The id is what a saved workflow binding resolves against.
- `execution` is exactly one transport (below).
- `tools` is an optional seed catalog. It lets Settings describe the server before the first connection and seed tool instructions. The server's live catalog remains authoritative; refreshing replaces the seed while preserving matching tools' user instructions and approval choices.
- The declaration never embeds a secret. The discovery scan reads the file as bytes and never executes it.

## Transports and configuration

MCP is the only tool wire protocol.

- **stdio** - `command`, `args`, optional `cwd`, optional `env` credential bindings. The process speaks MCP over standard input and output; diagnostics belong on standard error. It runs with the desktop user's OS authority. A relative command or `cwd` resolves inside the package folder; a bare command name resolves from `PATH`.
- **streamable HTTP** - `url` and optional `headers` credential bindings. The endpoint must be `http` or `https`.

`env` and `headers` reference stored credential metadata by name, never a value. The CredentialVault materialises the short-lived value only for the connection. The plugin's own configuration (endpoints, workflow ids, limits) is ordinary text carried in the arguments, the working directory, the URL, or a file the server reads.

## Optional skills

A plugin may contribute skill folders under `skills/<name>/SKILL.md`. They use the existing skill format exactly: YAML frontmatter with `name` and `description`, an optional invocation policy, and a Markdown body. A plugin contributes knowledge through the same discovery precedence as every other skill; it does not get to change that precedence. The reference ComfyUI plugin ships one such skill.

## Settings, and where a plugin is configured

One Settings section, **Tool Plugins**, owns everything about a plugin: the plugin folder listing with Refresh, Open plugin folder, Install plugin and Remove, and - once a package is added - its complete configuration. That configuration includes the MCP connection itself: the command or server address, arguments, working directory, credential bindings, per-function enablement, function instructions and per-function approval. A plugin is therefore never split between two sections.

The **MCP servers** section is for general, hand-configured MCP servers only and never lists a plugin-backed connection. Both are stored as MCP server entries, but a plugin-backed entry carries its package identity and is edited beside the package that produced it. The two groups are tracked as separate dirty domains, so editing a plugin marks Tool Plugins unsaved and editing a general server marks MCP servers unsaved.

Secrets are entered through the existing credential path and are never echoed into a projection or a log. A failed connection never rebinds or enables anything. An argument that looks like inline authentication material is refused; a secret belongs in a named environment binding that the server reads.

## Side-effect hints

A tool may declare `readOnlyHint` and `destructiveHint` annotations, exactly in the spirit of MCP tool annotations. They are hints, not a sandbox and not proof. They inform permission handling and approval presentation; the actual approval policy, filesystem grants and frozen per-Chat authority remain the authority. A read-only hint can permit an approval-free call only when it is paired with `destructiveHint` false.

## Trust

Installing or enabling a plugin is the user's trust act. Discovery is inert: a folder merely copied into the plugin folder is sourced, listed and disabled, and it stays disabled until the user adds it and turns it on. A manifest cannot invent an implementation, widen a credential reference, or grant itself authority. Local subprocesses run with the desktop user's OS authority - Aworkit provides no process sandbox for this transport and does not describe one.

## Folder, autosource and install lifecycle

- **Autosource** - one plugin folder is scanned on every Settings snapshot. Each direct child folder with a `tool-plugin.json` becomes one sourced plugin. Malformed packages are listed with their error and remain removable.
- **Refresh** - re-reads the folder. It is a read; it runs no code.
- **Open plugin folder** - reveals the Aworkit-owned folder in the platform file manager. The webview never supplies the path.
- **Install** - copies a user-chosen folder into the plugin folder. The copy is staged inside the plugin folder and renamed into place, so a failed copy never leaves a half-written package for discovery to read. A package that is already installed is replaced by the new copy. Symbolic links are refused and the package size is bounded.
- **Add** - copies a sourced plugin's declaration into the Settings draft, in the Tool Plugins section, as a disabled connection, preserving matching tools' user overrides.
- **Enable** - connecting the plugin loads its catalog and turns it on. This is the explicit trust act.

## Removal and update semantics

- **Removal never stops a workflow.** Removing a plugin deletes the folder and the saved connection that referenced it. At the next workflow start, configuration is re-resolved; a frozen tool whose plugin is gone is reported to the model as a missing capability and omitted, and the Run continues under the existing failure policy. Imported or exported Chats treat an absent plugin as missing.
- **A changed package never enables itself.** A plugin copied in as a new version is a new discovery. Existing saved bindings stay as they are until the user refreshes, reviews the new version and turns it on; the live catalog is re-read on the next connection so an improved server reaches the next pass.
- **Replacing a version keeps existing workflows valid.** The workflow document names a stable plugin identity; a new version replaces behaviour, not identity. A pin over the declaration detects drift for review - it is not a silent lockout, and it is never a claim about every dependency or a remote service implementation.

## Failure and degraded behavior

- An unreachable or unconfigured server is an explicit, named failure, not a fallback: the tool call returns an error result that names the endpoint and the fix, and the model is told the plugin is unavailable.
- A missing capability never ends the Run. It is omitted, warned about, and recorded as evidence.
- A plugin that speaks an unexpected protocol version is rejected at connection with the negotiated range, never silently downgraded.
- Configuration is never silently rewritten: a failed connect leaves the draft exactly as the user left it.

## Platform behavior

- Windows, Linux and macOS all use the same folder, manifest and MCP contracts. Executable resolution and file-manager reveal differ per platform but are core-owned and tested per platform.
- A command without a separator is resolved from `PATH`, so a Python or Node plugin works on every platform without shipping a binary.
- A local subprocess is a child of the supervised capability host; it is subject to the same cancellation, timeout, log isolation and crash containment as every other MCP server.

## Evidence

The concrete plugin identity, version, declaration hash, transport endpoint and each invocation's realised interface are recorded per Run. Editing a plugin never rewrites committed evidence; a later pass re-resolves configuration and records what it actually used.
