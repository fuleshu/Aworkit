# System One decision models: backlog design

**Status: backlog. Not approved for implementation.** This document records how a System One model *could* be integrated, where it would be used, and what would have to be true for it to earn its place. Its purpose is to keep the option alive and to let a later decision start from a concrete shape instead of a slogan. Nothing here authorises work.

**Verified / not verified.** The API shapes and model properties below are taken from the vendors' own published documentation and model cards; performance, price and calibration claims are theirs and unverified on Aworkit tasks. Treat every number as a hypothesis to measure, not a fact to build on.

---

## 1. What a System One model is, and is not

Two unrelated implementations currently share the label.

**Jev (TypeSafe AI)** is a hosted model with a narrow, well-specified REST API. One call evaluates a `state` against a map of typed `questions` and returns typed `answers`:

- `POST https://api.typesafe.ai/v1/systemone`, `Authorization: Bearer <key>`, one JSON body, one JSON response, no streaming.
- Three question primitives: `noul` (yes/no, returns a 0-1 probability), `choice` (returns the chosen option plus the full distribution), `score` (returns a probability-weighted value plus distribution and legend). Choice accepts at most 255 options; Score accepts 2-10 ordered levels.
- `choice` and `score` answers carry `confidence` derived from the distribution. The response also names the concrete model version (for example `jev-1.13.0`) and token usage.
- Errors are ordinary HTTP: 401, 422, 429 and 529, with exponential backoff for the last two.
- Text input only (strings, JSON objects, arrays of text). No images, no generation, no tools, no chain of thought. Published latency 70-500 ms; published input price $42 per billion tokens with output unmetered. Early access.

**CLM (Contrastive-LM)** is a self-hosted ranker and verifier, not a hosted service. `CLM-v0.1-8B` is Apache-2.0 and consists of two small heads (a state head and an action head) on top of a frozen Qwen3-8B encoder, trained with a bidirectional InfoNCE objective:

- The encoder is served by vLLM as an **OpenAI-compatible `/v1/embeddings`** endpoint.
- The heads are served by the `contrastive-lm` Python package (`clm-serve`, default port 8700), which exposes a `system_one` call with the *same* Choice/Score/Noul shape as Jev, plus an `engine.rank(query, candidates)` call for ordering a supplied candidate list.
- It cannot generate. It scores only the candidates it is given, and its probabilities are relative to that set.
- It is encoder-locked to Qwen3-8B last-token-pooled embeddings, and the published verifier results come from *fine-tuned* heads, not the zero-shot checkpoint. A larger multimodal CLM is announced.

### 1.1 There is no standard, but there is a convergent contract

Neither model speaks OpenAI Chat Completions. However:

- CLM's encoder half *is* OpenAI-compatible (`/v1/embeddings`).
- Jev and CLM independently adopted the same semantic contract: *state + typed questions in, typed answers with probabilities and confidence out*.
- TypeSafe itself publishes `system-one-adapter-python`, a drop-in implementation of that same contract backed by OpenAI, Anthropic or Gemini. Their own position is that the interface is the stable artifact and the model is the swappable part.

**Consequence for Aworkit: one contract, N thin backends.** A System One adapter is a single bounded, non-streaming POST with a small JSON body - unlike the chat adapters, it needs no SSE handling, no tool-call state machine, no image positioning and no prefix accounting. The right abstraction count is one contract plus thin per-backend modules, not one node type or one plugin per vendor.

## 2. The case, and its honest limits

The mechanism is not the model, it is the *price of a judgment*. Routing and verification research already established that a cheap, **calibrated** quality estimator is the missing ingredient: cascades matched frontier quality at very large cost reductions, and the theoretical result is that a cascade dominates pure routing *when the estimator is calibrated*. A System One model is a claim to be that estimator at a cost and latency where it can run on **every** decision rather than on a sampled subset.

Why this fits Aworkit specifically: **a System One model needs a bounded answer space, and the workflow graph is a machine for producing bounded answer spaces.** Tier ids, tool bindings, node types, branch targets and compaction policies are already finite enumerations frozen per revision. The graph supplies the option set the model lacks; the model supplies judgment the graph lacks. The workflow editor supplies the authoring surface, and the committed per-node evidence supplies the calibration loop.

Honest limits, stated once so the document is not read as advocacy:

- **It cannot cut the dominant cost.** The expensive term in an agent Run is the context carried through it. A $0.00008 judgment does not move a 100k-token turn. The saving available here is decision overhead and, via admission control, context *volume* - not the per-call price of the work itself.
- **It cannot do open-ended work.** No generation, no novel reasoning. Benefit is confined to the bookkeeping around the work: routing, verifying, admitting, escalating.
- **Calibration is load-bearing and unverified.** Confidence is a model-level property; a user can move a threshold but cannot fix a miscalibrated distribution. Vendor calibration is measured across groups, not per answer.
- **Routing buys cost, verification buys quality, decomposition buys both.** Mis-routing is a quality *loss*, so a router alone is not an improvement over a fixed policy in expectation - it is a bet that per-input information beats a static assumption.

## 3. The decision contract (the stable artifact)

Define one provider-neutral capability. Suggested shape, to be finalised before implementation:

**`DecisionQueryV1`**

- `state`: a bounded serialised value (string, object or array). Bounded by an explicit byte cap before dispatch, mirroring the existing provider input bound.
- `questions`: an ordered map of `{ id -> { type: noul | choice | score, instructions, criteria } }`, validated against the primitive rules (choice options <= 255, score levels 2-10), bounded in count and size.
- `defaults`: a **declared** fallback answer per question, authored in the workflow. This is what makes the node safe: unavailable backend or below-threshold confidence resolves to the declared default, never to an invented option and never to a host fallback (the existing no-provider convention).

**`DecisionAnswerV1`**

- Per question: `type`, the selected `choice` or `score` or `noul` value, the full `probabilities`, `confidence`, and a `legend` where applicable.
- Response metadata: backend identity, concrete model version, usage, latency, and whether the answer was native or fallback.
- Validation: probabilities sum to 1 within tolerance, every returned key exists in the requested criteria, confidence within 0-1. A response that fails validation is a typed failure, not a partial answer.

**Placement.** A new `system_one/` module in the capability host, reusing the existing bounded JSON transport (bounded body, connect/request timeouts, 4 MiB response ceiling, sanitised errors). It must **not** be modelled as a `ProviderEnginePortV1` candidate or a model-tier entry:

- The chat contract cannot represent a decision without stringifying it into `AssistantOutput` and re-parsing it, and it requires exactly one usage event and streamed text. That is precisely the lossy coercion System One models exist to remove.
- A decision model has no messages, no tools, no streaming, no images and no notion of a conversation turn.

**Backends behind one trait:**

- `jev` - the hosted endpoint described in section 1.
- `clm` - embeddings via an OpenAI-compatible endpoint plus head scoring (or `clm-serve`), including the candidate-ranking call.
- `llm` - the same contract implemented by prompting an existing Aworkit provider for schema-constrained JSON, validating against the question schema and normalising the distribution. TypeSafe ships exactly this as their own adapter, and it matters strategically here: it makes the node, the ranking and the calibration loop exercisable **today**, against providers already supported, before any vendor access exists - and it produces the same-questions/different-backend evidence table that would justify or reject Jev and CLM.

Backend selection is frozen per node the same way provider selection is today, and the concrete model version is recorded per decision.

## 4. Workflow integration

### 4.1 A new node type

The workflow node catalog (`KNOWN_NODE_TYPES`, currently input, loop, agent, model_call, tool, external_agent, condition, parallel, approval, output, wait, completion) gains a decision node registered through the typed node runtime so each node type maps to a pinned executor contract.

**Configuration** (bounded and validated like every other node):

- the question catalogue (ids, types, instructions, criteria);
- the state source - explicitly which incoming value is serialised as `state`;
- the declared default answer per question;
- the backend binding and its limits.

**Output**: a typed decision record injected into the graph value flow, so an existing condition node can branch on it. Conditions stay deterministic; the model supplies only the judged values. This keeps the fuzzy part in the model and the authority in the predicate.

**Predicate extension**: the current predicate kinds are `always`, `exists`, `eq`, `neq`, `and`, `or`, `not` with a nesting depth limit. Thresholding a probability or a confidence needs ordered comparison (`gte`/`lte`) and a defined path convention for addressing `answers.<id>.choice`, `.score`, `.noul`, `.probabilities.<option>` and `.confidence`. Without this, thresholds can only be expressed as equality, which is useless for a calibrated score.

### 4.2 When is the decision made? (the dimension that organises everything)

The useful framing is not *whether* a decision is allowed but **at which information cutoff it is taken**. Every step later a decision is made, the more it knows:

- **once, at Run start**, from the user's input - cheapest to adopt, sees almost nothing;
- **per step**, from actual intermediate state - strictly better informed (the cheap path already tried and looks shaky, so escalate), and the point at which cascades earn their numbers;
- **over a candidate set enumerated at freeze**, ranked rather than chosen - the natural frame for CLM.

Late is not free, and the cost is per dimension rather than global: selecting a tool among already-configured bindings is nearly free (it only changes which schemas enter the request), while selecting a *tier or provider* implies a credential lease per candidate, per-candidate context capacity, and the loss of prefix-cache reuse across a hop. Those are engineering consequences to accept deliberately, not reasons to decline. Nothing requires a uniform commit point: enumerate the cheap dimensions up front and decide the expensive ones as late as is affordable.

### 4.3 What can be selected (a catalogue to grow)

Grouped by the axis each decision actually predicts:

- **Capability** - model tier, reasoning effort, thinking on/off, native agent versus external agent.
- **Admission** - which tools and MCP servers, which instructions or persona, which context sections.
- **Control flow** - which branch, repeat or move on, fan-out width, delegate to a subagent or run inline.
- **Effort and budget** - max output tokens, search depth, source count, retry allowance, compaction policy.
- **Governance** - approval mode for what happens next.
- **Proceed or not** - escalate, abstain, ask the user.

Two filters make this list sortable:

- **Recoverability.** Effort, search depth, instructions and compaction degrade gracefully; a missing tool or an insufficient tier hard-fails. Experiment with the recoverable ones first.
- **Error-cost asymmetry, which should set the default rather than the question wording.** For tiers, over-routing costs money and under-routing costs correctness, so unsure escalates *up*. For tools, over-enabling costs context that the compression path already manages while under-enabling costs capability and can hard-fail the node, so plausibly-relevant tools default *on*.

**Ask tier questions about difficulty, not subject matter.** "Is this a programming task?" is a domain question and predicts which tools are needed. "Is this simple / does it need an expert?" is a difficulty question and predicts which tier is needed. Topic does not predict capability need: a trivial change in a subtle repository still needs the strong tier. Difficulty is better predicted by ambiguity, how much context is required, how many independent concerns are involved, and whether a wrong answer is recoverable.

### 4.4 Authority and evidence

- A decision may select **only among alternatives already enumerated for the current revision**. It may never widen authority. A selection that would add a tool binding, a credential reference, an approval-mode change or a longer deadline is not a decision - it is a revision rebind and needs the same explicit user consent and authority-delta presentation that rebinding already requires.
- Every decision is committed as evidence: the questions asked, the full distribution, the confidence, the option selected, the alternatives not selected, the backend identity and concrete model version, whether a fallback was used, and the outcome link (below). A branch whose reason is not recorded makes a Run unexplainable, and the existing failure-policy principle applies - a bound truncates a notice, never the work and never the reason.
- Because a decision steers the graph, its executor belongs to the node runtime and follows normal node failure semantics: a decision failure resolves to the declared default and continues, rather than ending the Run.

## 5. Tools

Three distinct uses, ranked by value:

1. **Admission control - the highest-value use.** Judge relevance and sufficiency *before* content enters context: is this retrieved page sufficient to answer the current question, is this tool result relevant, is this excerpt needed. This attacks the dominant cost term (context volume) rather than the per-call price, and it improves quality by keeping noise out of the window. Natural insertion points are the existing bounded selection steps in web search results, retrieval and tool-result admission. There is a real fallback available today: the current relevance selection is a BM25-style lexical ranking with no embeddings, and a contrastive re-ranker is a direct upgrade over it. When the backend is unavailable or unconfident, fall back to that deterministic ordering - never to nothing.

2. **Ranking and pruning candidates.** Ordering a supplied candidate set - search results, retrieval pages, tool names, best-of-N agent outputs, subagent results. CLM's rank call is purpose-built for exactly this. Note that its *relative* probabilities are the correct semantics here: in a frozen candidate set, "relative to this set" is not a limitation but the definition of the question. Keep candidate sets bounded (Jev caps a Choice at 255 options) and never read a relative score as an absolute probability.

3. **Tool and domain selection.** Choosing which tool bindings or MCP servers an Agent is offered, and thereby which schemas enter the provider request. Two existing constraints must be respected rather than re-derived: the tool interface a provider is offered is the acting pass's frozen selection with recorded calls re-pointed where a capability survives, and a recorded call the new selection cannot represent is declined and committed as a fact rather than rewritten. Changing the offered set also interacts with prefix stability, so this use should be adopted later than admission control, and its default should be inclusive.

**Do not place a decision model on the authority path as an authoriser.** It is fast enough to look attractive as an approval gate, but a probabilistic component may only *escalate to review*, never authorise something the current policy would not. Its failures there are also the least visible.

## 6. Compaction

Compaction is the clearest quality-and-cost use after admission control, and it is where the current mechanism is most heuristic.

Today, selection is by recency, size and lexical relevance, with several hard invariants: complete tool exchanges are indivisible units, live-zone surgery preserves cached wire prefixes, and the budget model caps what a compaction may free and spend.

A decision model could be consulted, always with the existing invariants preserved:

- **Exchange retention.** "Is this closed exchange still needed to answer the current objective?" - per exchange or per group, with confidence, and with the deterministic rule as fallback. A low-confidence result must not override an indivisible-unit boundary.
- **Excerpt sufficiency inside a retained unit.** "Is this excerpt sufficient for the purpose it is retained for?" - the same judge used for tool admission, applied inside the retained span rather than at the boundary.
- **Protection of fragile facts.** "Does dropping this lose a protected fact, identifier or constraint?" - a second, independently asked question, combined in the graph rather than in one prompt.
- **Summarisation route selection.** Which tier or backend performs a summary is itself a decision point, and a cheap one at that.

**Hard constraints on this use:**

- A judge may inform *selection only*. It may never rewrite bytes in place, and it must not disturb the prefix-stability guarantees that make provider caching work.
- The budget model still governs. A judge arguing for retention argues; it does not override the cap, and it cannot make a compaction that frees nothing look successful.
- Omitted content must remain retrievable, and each kept or dropped unit must record *why*. Otherwise compaction stops being explainable and the existing truthful-omission guarantees decay.
- Cost discipline: consulting a judge per unit must be cheaper than the tokens it saves. Batch questions across units in one call where the primitive allows it (parallel independent questions are the intended usage).

## 7. The calibration loop, and why the editor makes it viable

This is the part that makes the whole feature more than a wiring exercise, and it is where Aworkit has an advantage a chat application cannot match.

Committed run events already carry a node identity, the workflow document is frozen per revision, and per-node activity is durably recorded. Once a decision node exists, **every Run is a labelled data point at a stable, versioned address**. An ad-hoc prompt has no identity to accumulate statistics against; a workflow node has an identity, a revision and a history.

The loop:

1. **Predictions** are recorded automatically as decision evidence.
2. **Labels** come from outcomes the workflow already produces - an escalation to a stronger tier, a tool error, a failed test, a rejected approval, a user edit. Each decision node should be able to declare *which downstream outcome counts as this decision having been right*; without that declaration the loop collects predictions with no verdicts.
3. **Presentation** belongs in the workflow editor, beside the node: the current threshold, the observed escalation rate, the accuracy at that threshold, and the confidence distribution for this revision.
4. **Keying is mandatory**: statistics must be keyed by (workflow revision, node id, question id, backend model version). Mixing any of these silently averages different prompts, and the resulting number looks healthy while being meaningless.
5. **Recalibration is a possible future step.** Raw confidence is a model-level property. If it proves miscalibrated per task, compensating with a per-decision calibration curve is a real feature - and it is only possible because decisions have stable identities.

**Evaluation without a research programme.** Because routing on and routing off differ by one node setting, the same graph can be run both ways with outcomes recorded. The workflow becomes its own evaluation harness, and the user tunes from evidence rather than argument. The honest risk to guard is the opposite failure: hand-tuned thresholds that work on the cases someone happened to try. An editor must not present a threshold as *configured* without presenting what it did.

## 8. Open questions to resolve before any decision

- Single resolved binding versus per-node binding sets; per-candidate credential leases and per-candidate context capacity (the compaction policy is currently expressed as a share of one routed window, which is wrong if candidates differ).
- The commit point per dimension, and whether routing at Run start is enough for the first increment.
- Whether the decision surfaces as a node type, a capability invocable by tools and compaction, or both (the likely answer is a capability plus a node type that wraps it).
- Backend dependency strategy: Jev is early access and contact-sales; CLM is self-hosted and on a public scaling ladder. The contract, not the vendor, must be the durable artifact.
- Evaluation protocol: which decisions are measured, on what data, and who owns the thresholds.
- Security and bounds: what may enter decision state (no secrets), response-size ceilings, reuse of the existing bounded transport, and no widening of authority.

---

## 9. Non-goals

- Not a chat provider and not a member of the model tier catalog.
- Not an authoriser on the authority path; it may escalate, never grant.
- No generation, no open-ended reasoning, no tool calling of its own.
- No silent widening of authority, and no host fallback when a backend is unavailable - the declared default applies.
- Not required for any current milestone. This is backlog.
